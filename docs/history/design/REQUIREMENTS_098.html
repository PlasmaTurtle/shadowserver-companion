Release requirements · 10 November 2026

Shadowserver Companion 0.9.8

Independent entities and leads, one home for notification work, fast content locks, concise reports, readable evidence, and useful contact discovery.

Recommended baseline for discussion. Based on Kyle’s requested changes and a read-only review of the supplied 0.9.7 source. These are requirements, not claims that 0.9.8 has been implemented.

Primary design decision: Workspace owns investigations and notification workflows. Entities owns organizational records and contacts. Leads owns incoming findings awaiting action. Opening or maintaining an entity must never require opening or creating a notification.

1. Navigation and ownership

DestinationPurpose and expected behavior
WorkspaceRenames the former Today view. Overview, investigations/notifications, report builder, pending notification, delivery, closing, and completed packages live here. Keep these as internal views and stage filters. Every link to a notification routes here and highlights Workspace.
EntitiesIndependent entity list and detail pages: name, address, associated hostnames/IPs, contacts, notes, attribution history, and linked notifications. Badge counts distinct entities needing review, once per entity.
LeadsIncoming findings awaiting action. Shows known-entity association, New entity, or Match needs review. Opening a lead shows the finding and its source observations, not a report editor.
AttributionExisting attribution work and supporting evidence. Remove “review” from the destination name while retaining actual unresolved-review states.
Shadowserver DataImport report files or retrieve reports through the API. Both acquisition methods feed the same intake and source-preservation pipeline.
Eclipse ObservatoryMap, density, and metrics. Entity links open Entities; lead links open Leads; notification links open Workspace.
LibraryExisting explainer library and editing functions.
Activity / SettingsRetain their functions. Put build information and detailed diagnostics in Settings/About.

Remove the separate top-level Shadowserver Notifications destination and place Certified reports within Workspace’s completed view. The requested investigations area is a real Workspace view, without adding a competing top-level destination.

R1 · Canonical navigation

  • Separate entity, lead, and notification routes and screen state. Use one canonical route for each notification, regardless of where it was opened.
  • Browser Back/Forward, refresh, and direct links preserve the selected record and internal tab. Return navigation restores list filters and scroll.
  • Track unsaved edits in every form, including entity name. Background refresh cannot overwrite edits. Save and Ctrl+S target the active record.
  • Refresh sidebar counts independently of visiting Workspace. Counts use explicit, consistent definitions; the Entities badge is not an in-progress report count.

Acceptance: an entity with no notification can be opened and edited; all notification links highlight Workspace; history and refresh work from each destination; no entity edit is silently lost.

2. Entities, leads, and workflow

R2 · Entity records remain independent

  • Reuse the existing entity IDs, profiles, hostnames, attribution history, and entity-owned contacts. Decoupling does not require replacing historical records.
  • Allow entity maintenance and contact discovery without an active report. Use the entity’s associated website/domain for discovery.
  • Contact changes and internal notes must not reset report reviews or bump unrelated report content revisions.
  • Report-relevant identity changes can be brought into an editable draft explicitly. Frozen sections and certified packages retain their recorded values until the applicable content is reopened or a new revision is created.
  • Entity review concerns missing or unresolved business details. Discovered contact suggestions do not create review obligations.

R3 · Leads are findings waiting for action

  • Retain relevant incoming finding groups in Leads before notification work begins. Show reported hostname, IP(s), finding/CVE or EOL technology, dates, source, observation count, attribution state, and associated entity.
  • Group related observations for readability while preserving every original row and its source reference.
  • Automatically associate an unambiguous stored hostname/domain or established entity-to-IP relationship. Display the matching basis unobtrusively.
  • Raw shared-hosting IP overlap alone is insufficient for an automatic association. Conflicting hostname/IP matches or multiple possible owners show Match needs review. Unmatched records show New entity.
  • Association and attribution remain separate: matching a known entity does not manufacture a new attribution validation.
  • Importing or associating a lead must not automatically create a notification. A single Start notification action creates the work item; Add to active notification assigns selected findings to a compatible editable case.
  • New observations do not silently reopen closed cases or modify frozen reports. Duplicate imports do not create duplicate leads or notifications.
  • Keep simple defer/dismiss handling so the queue represents findings still awaiting action. Existing completed and deferred history remains accessible.

Acceptance: imports populate Leads without new cases; an established entity association appears automatically; ambiguous/shared-IP cases remain unresolved; one action starts work in Workspace; existing historical cases survive migration unchanged.

3. Report Builder

R4 · Freeze locks content immediately

  • Freeze saves the section’s content snapshot, selected source references and hashes, author, timestamp, and deterministic content fingerprint.
  • Freeze performs no document pagination, SVG/PNG artwork generation, PDF/DOCX rendering, render-worker launch, or rendered-page save.
  • Preview is explicit. Final package generation renders the selected frozen content. Rendering failure leaves content and locks intact and can be retried without re-freezing.
  • Retain validation of required content and stale-edit protection. Avoid network retrieval during freeze.
  • Version the content-only fingerprint contract. Existing 0.9.7 frozen sections and packages remain readable with their original evidence and hashes.
  • Separate presentation options from content review. Changing appendix inclusion or compact layout does not reopen unchanged introduction, vulnerability, attribution, information, or closing sections.
  • Final certification records the chosen presentation version and actual output hashes. Already certified output remains immutable; changed output becomes a new revision.

Acceptance: instrumentation records zero renderer calls during all five section freezes. Proposed Windows performance target: typical acknowledgment under one second, p95 under two seconds on an agreed representative case. Verify the actual workstation timing rather than promise hardware-independent performance.

4. Appendix and evidence packages

R5 · Compact recipient appendix

Use record-type templates with meaningful fields rather than printing the raw source structure.

Record typePrinted content
ObservationReported hostname, IP, relevant port/protocol, finding/CVE or EOL technology/version, observation date/range, source reference.
AttributionReported asset, matched evidence, method/source, lookup date, relevant recorded decision.
Vulnerability / EOL findingIdentifier or technology, relevant facts, source and date; reuse report references rather than repeat full explainers.
ReferencesPublisher, title, URL, and relevant date; list shared references once.
  • Omit empty/default fields, parser metadata, internal paths, raw response bodies, and repetitive descriptions. Preserve meaningful zero/false values.
  • Group repeated observations with identical relevant findings/assets, retaining date ranges, counts, and traceable source references.
  • Flow sections continuously, omit empty sections, and remove forced new pages per category. A short appendix does not need a standalone index page.
  • Use readable type, sensible table widths, repeated table headers, and controlled row breaks. Long cases may take additional pages; never drop relevant findings to meet a page target.
  • Retain the appendix include/exclude control and the existing available-upon-request footer when excluded.
  • Complete source records remain in the internal package even when not printed in the recipient appendix.

Acceptance: no empty appendix pages; representative one-asset appendix targets one to two pages; record before/after page counts for small and larger fixtures and verify that all relevant findings, attribution, and references remain accessible.

R6 · Unified internal Evidence Record

Each final package has one obvious, offline Evidence_Record.html entry point. Extend the existing attribution evidence-reader pattern across all evidence types.

  • Start with a concise package summary and index. Use the same readable template for observations, attribution, CVE/non-CVE references, contact research, supplemental JSON, screenshots, and chronology.
  • Each record presents: title/type; actual finding; relevant values; source and capture time; associated asset/finding; collection outcome; link to the original record.
  • Collapse full hashes, internal identifiers, field paths, response metadata, and verbose raw content. Keep relevant failed/partial collection outcomes available without overwhelming the principal finding.
  • Preserve original JSON/source bytes alongside the reader. Generate summaries deterministically from stored fields; no fresh retrieval or invented narrative.
  • Include author/timestamps and lock/certification chronology in consistent tables. Keep collection time distinct from source observation and review times.
  • Support a concise printable view. Unknown JSON types receive a readable labeled-field fallback rather than an unreadable blob.
  • Use portable relative links, escape captured text, and do not execute scripts from captured pages. The reader works after extracting or moving the package and does not need the application or internet access.
  • Clearly distinguish recipient documents from internal evidence in the package structure and labels. Keep the appendix field projection and evidence reader backed by the same presentation model.

Acceptance: a reviewer can identify the finding, asset, source, capture time, and original evidence from one index; every JSON evidence type is covered; relative links work; retained bytes and hashes match; partial captures are accurately labeled.

5. Contacts

R7 · Actual contacts first, immediately usable

Merge known entity contacts, previously used contacts, manual entries, and newly discovered contacts into one deduplicated list. Show known contacts immediately, before any lookup finishes.

Contact foundsecurity@wasabi.comSecurity contact

support@wasabi.comTechnical referral found

Details · Sources, dates, capture status, and additional findings

Illustrative presentation using Wasabi’s published addresses. It is not a screenshot of a completed 0.9.8 feature.

  • Show Contact found and the actual email, phone number, or form link prominently. Label the actual purpose accurately: security contact, IT/webmaster referral, product support, or general contact.
  • Collapse sources, timestamps, coverage, diagnostic detail, and lower-priority findings under Details. Remove next-step instructions, review counts, duplicate best-route cards, and repeated explanatory prose.
  • Remove verify/confirm/review/adopt prerequisites from the UI, API, readiness logic, and backend. A discovered contact is immediately available for copy, open, and autocomplete.
  • One selection fills the relevant blank fields. Do not overwrite an entered value or send any communication automatically.
  • Keep optional preference/hide controls unobtrusive. Preserve historical review and delivery information, without turning it into a required step.
  • A known bounced or unusable contact stays identifiable and is not silently promoted by rediscovery. A saved general contact must not prevent a requested search for a better technical route.
  • Finding contacts does not imply delivery or completion of a notification. Preserve this distinction in stored workflow state without adding review buttons.

Acceptance: zero verification clicks before selecting a suggestion; a known contact appears on the entity and a new notification without rerunning discovery; contact changes do not invalidate frozen report sections.

R8 · Capture and extraction reliability

  • Use one shared limit policy across retrieval, persistence, evidence reading, export, and restore. Proposed initial benchmark envelope: 4 MiB per page and 12 MiB per run, retaining the 30-second deadline and bounded request count. Tune from measured Wasabi and existing-company results before release.
  • Keep the smaller error-body allowance so a large error page cannot consume the useful capture budget.
  • Extract complete emails, phone numbers, and fully captured contact elements even when the page is partial. Omit cut-off values and avoid assigning a purpose from unfinished or neighboring context.
  • Separate discovery success from capture completeness: one failed optional page must not erase a useful contact or change the headline to overall failure.
  • Describe the actual issue, such as page size limit, parse failure, or unreadable content. HTTP 200 must never be presented as the cause of a failure.
  • Avoid duplicate byte-limit/parser-limit warnings for the same truncation.
  • Improve prioritization of company-published trust, security, disclosure, contact, and technical-support paths within the bounded search. Preserve relevant external reporting links and their first-party source.

Acceptance: default Wasabi discovery returns its published security contact and support referral with correct sources/categories; complete contacts before a cutoff survive; cut-off values do not; successful findings survive optional-page failures; enlarged captures save/export/restore correctly. Re-run the existing ten-company cases with explicit coverage and correct departmental classification.

6. Shadowserver Data and interface language

R9 · Files and API use one intake pipeline

  • Files retains upload/inbox import. API provides credential configuration, available report selection, date/report-type filters, retrieval progress, cancel/retry, and import results.
  • With no credentials, show a simple Not configured state. Build against documented contracts and offline fixtures now; mark authenticated acceptance pending until credentials are available.
  • Preserve original report bytes, report identity, acquisition receipt, and source hashes. Both paths share duplicate detection, parsing, association, and lead creation behavior.
  • Retain source observation date, report date, and retrieval time separately. Do not substitute download time into the established narrative-date rule.
  • Keep credentials out of reports, evidence, and diagnostic output. Do not imply that fixture tests validate a live account.

Acceptance: file and API fixtures produce equivalent leads with acquisition provenance; repeated retrieval is idempotent; absent/invalid credentials, interrupted retrieval, and malformed files have clear recoverable states. Live authentication and account coverage remain the only credential-dependent checks.

R10 · Remove redundant and development-oriented copy

  • Apply Workspace, Entities, Leads, Attribution, Shadowserver Data, Eclipse Observatory, and Library consistently across navigation, page headings, breadcrumbs, dialogs, empty states, and links.
  • Remove the shared YOUR WORKSPACE eyebrow, duplicate titles, slogans, obvious descriptions, and unnecessary instructions.
  • Preserve functional field labels, accessible names, useful error messages, actual source dates, and essential missing-information states.
  • Move build/validation detail to About/diagnostics. Retain an unmistakable synthetic-data indicator in demo mode and accurate release status; a copy cleanup does not establish stability.
  • Review the actual rendered application in both themes and normal window sizes. Do not limit the audit to string replacement.

8. Release acceptance and build order

  1. Separate record ownership and navigation. Establish entity, lead, and notification routes; stop automatic case creation; migrate existing records without losing IDs or history.
  2. Remove freeze rendering and global invalidation. Introduce versioned content locks and preserve historical frozen reports.
  3. Build one evidence presentation model. Use it for the compact appendix and offline internal evidence reader.
  4. Simplify and repair contacts. Remove gates, show known contacts, preserve complete partial-page findings, centralize limits, and verify Wasabi plus prior company cases.
  5. Integrate API acquisition and finish copy cleanup. Exercise documented offline cases and leave live-account testing explicitly pending credentials.
  6. Run full operator journeys. Import → Leads → association/attribution → start notification → freeze → generate → deliver-record → closing; also independent entity/contact maintenance.

Release checks must include real-browser navigation/editing, actual rendered PDF/DOCX inspection, the agreed Windows freeze timing, and Windows retain-data upgrade. The previous release documented that interactive browser validation had not run; unit tests alone do not establish that the new navigation is polished.

Migration acceptance preserves entity/case/contact IDs, original observations, attribution evidence, existing frozen reviews, delivery history, certified package bytes/hashes, and backup/restore behavior. Repeated imports and operations remain idempotent. Existing reports are not rewritten as a side effect of upgrading.
